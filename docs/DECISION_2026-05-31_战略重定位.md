# WhyWiki 战略重定位决策记录

- 日期：2026-05-31
- 决策类型：产品方向重大转向（pivot / 降级为组件）
- 参与者：晓磊（创始人）、Starry / opc（产品负责人）、Codex gpt-5.5（外部专家 / 魔鬼代言人）
- 决策方式：OPC 工作流"需求层多声音讨论"的首次真实跑通
- 状态：已达成方向共识，定位为**假设**，待一次真实 dogfood 验证

---

## 一、一句话决策

**停止把 WhyWiki 作为面向外部用户的"需求的 git"独立产品继续投入；将其重定位为 OPC 工作流中的「需求演进记忆层」——一个把 idea→产品的对话流，转化为给 opc-dev 的"当前需求快照"和给人看的"演进/裁决记录"的内部组件。创始人本人是第一个、也是唯一能真实 dogfood 的用户。**

---

## 二、原产品定位与现状（事实）

- 定位：WhyWiki = "需求的 git"。代码有 git 管迭代，项目文档/需求没有工具管变更历史。
- 现状：开发约 3 周（2026-05-10 → 05-29），111 次提交，约 5660 行 Python + 6881 行前端。
- 功能首板完整：本地摄入、确定性事实抽取（带证据指针）、四类冲突检测、需求生命周期、裁决记录、Wiki 生成、交接包、带证据问答、完整 Web UI、GitHub/Gitea 真实登录。
- 关键信号：**创始人本人从未拿 WhyWiki 跑过任何一个真实项目**，包括 dogfood。这不是 demo，但也从未被真实使用。

---

## 三、看空论据（三方共识，导致放弃原定位）

1. **致命缺口**：最有价值的需求（漂移后的最新版）往往不在文件里，而在沟通/会议/聊天里。WhyWiki 只摄入静态本地文件，最有价值的那部分进不来，且没人会事后手动录入。
2. **没有强制函数**：git 成立靠"不 commit 就没法协作"的强制力；"记录需求变更"没有任何强制力，不记项目照样推进。无强制力的纪律必然烂尾，而过期的需求 wiki 比没有更糟。
3. **变更成本暴跌 → 管理价值暴跌**：两年人肉项目里改需求=重写几个月代码，漂移是灾难、值得管；AI 两周 POC 时代改需求=重生成一版，"记录漂移历史"价值变薄。
4. **在解决正在消失的问题**：原始痛点源于"AI 未普及、纯人肉、项目周期长"的时代。AI 越强，这个具体痛点形态越是被科技发展覆盖，而非被工具解决——这也解释了为何一直没人做类似产品。
5. **新形态被大厂占据**：残留的需求价值变成"喂给 Agent 的 spec"，而这正是 Kiro spec、GitHub spec-kit、Cursor rules 在抢的地盘，大厂有最强动机自己做掉输入端。
6. **建造者无法 dogfood**：创始人现为独立开发者，手上没有长周期、需求漂移的真实项目，无法验证自己为过去的痛建的产品。

---

## 四、反方论据（Codex 作为魔鬼代言人挖出，打破双人共识盲区）

被指派站对立面后，Codex 提出两条关键反驳：

- **AI 降低的是编码变更成本，不是责任/范围变更成本。** AI 时代客户更容易一句话改方向，需求漂移反而更高频。痛点从"大型漂移"变成"小型高频争议"，价值没消失，只是换了形态。
- **不要跟大厂比"写 spec"，要做"spec provenance"。** 大厂做更顺滑的 spec authoring；WhyWiki 应做大厂不愿做、但 Agent 很需要的那层——来源证据、冲突检测、验收口径、变更裁决。**站在所有 Agent 之前，而不是成为某一个 Agent 的 UI。** local-first、vendor-neutral、evidence-grounded。

Codex 原始提案是 pivot 成"外包交付证据账本"。**此提案被 PO 否决**：目标用户（乙方外包团队）创始人本人不属于，会重蹈"建造者无法 dogfood"的死循环；且与创始人"排斥反复改需求的外包项目"的明确偏好冲突。但其"站在 Agent 之前的证据化需求闸门"这一半，被采纳并接入 OPC 工作流。

#### 外包账本提案的深度否决（创始人补充，两条独立否决线）

事后创始人补充了两条更根本的否决理由，任意一条单独成立即可杀死该提案：

1. **市场/需求轴（硬伤）**：证据账本的全部价值建立在"甲方验收时翻旧账"这个低频事件上。但现实是——一半以上项目验收时甲方并不胡搅蛮缠；且甲乙双方多半想长期合作，翻旧账本身就是关系破裂信号，理性双方都会回避。这导致一个自相矛盾：**最需要证据账本的场景（恶意甲方），恰恰是创始人最不想接的那类客户。** 它服务的是创始人主动排斥的人群。Codex 看不到这层，因为它不掌握创始人画像。
2. **定位轴（同义反复）**：WhyWiki 一旦降级为 OPC 内部组件，"对外打官司/向甲方举证"这个 use case 直接消失——创始人不需要拿账本跟自己打官司。这条几乎无需论证。

**关键区分**：被否决的是"外包纠纷"这个 go-to-market 框架（卖给谁、解决谁的官司），不是底层能力。Codex 洞见中真正值钱的部分——**带证据指针地记录需求/裁决的演变**——已作为"演进/裁决记录"保留在重定位方案中。扔的是外壳，留的是内核，本次否决不损失任何资产。

**元结论**：Codex 擅长发现机制（"可以做一个证据账本"），但判断不了这个机制该不该存在、为谁存在——那是产品负责人的活，必须拿创始人画像和真实市场去过滤。再次印证多声音工作流原则：Codex 当技术反方很强，定产品方向得 PO 兜底。

## 五、最终重定位（共识收敛 + 创始人两个关键想法）

WhyWiki = **OPC 工作流的"需求演进记忆层"**。

- **输入端的根本改变**：输入不再是静态本地文件，而是 **idea→产品的对话流**。从创始人提出一个 idea 那刻起，由一个模型根据讨论内容持续捕获并更新需求演进。这一刀直接焊死"看空论据 1"（why 不在文件里）——产生 why 的现场（对话）本身成为输入端，自动捕获，不靠事后录入。
- **输出端分层**：
  - 顶层：给 opc-dev 的"当前需求快照"（opc-dev 只看最顶层需求）。
  - 中间层：给人看的"需求演进/裁决记录"（项目从 idea 到可产品化的完整变更轨迹）。
- **强制函数解决**：不再是"逼人记 wiki"，而是"没有干净需求包，opc-dev 不开工"——强制力来自工作流纪律，且记录由模型自动产生，人只在裁决点拍板。
- **dogfood 解决**：创始人每跑一个 OPC 产品就用一次，是第一个也是真实的用户。
- **被吞并风险解决**：不与大厂比写 spec，做喂给任意 Agent 之前的证据化校验，local-first、vendor-neutral。

### WhyWiki 的体面归宿
WhyWiki 从"独立产品"退化为"OPC 的一个组件"。退化过程本身会暴露它的**冗余部分**（泛需求管理外壳、GitHub/Gitea 登录等）和**缺失部分**（对话流摄入、与工作流的交接契约），同时**验证其核心概念有意义**——确定性事实抽取＋证据指针＋冲突检测＋裁决记录＋交接包。把验证过的内核活下去，丢掉没人买单的外壳。

---

## 六、被推迟/降级的想法（防止过度兴奋，PO 留痕）

1. **"派模型持续更新需求演进"组件**：先不建。下次真 idea，由 opc 在对话中**手动维护**一份需求演进记录，验证"是否真有人回头看"。有用再自动化，无用则省下一个组件。理由：避免重蹈"先建基础设施"的坑。
2. **"整理经验做成资料售卖"变现**：最远、最弱的假设，叠加了三个未验证前提（数据攒够、经验可提炼、有人付费）。当作 free optionality——只要演进记录本身有自用价值，能否变现是白捡的，现在不为它做任何设计。

---

## 七、可复用核心资产（若做减法，优先保留）

按价值排序（Codex 评估 + PO 确认）：
1. 确定性事实抽取 + 证据指针（最核心，可作独立 evidence layer）
2. 冲突检测器（多个 latest / API 不一致 / 模型漂移 / 文档与代码不一致，可包装成 requirement-lint）
3. 裁决记录 / 需求生命周期（从"维护需求库"改为"记录争议如何被裁决"，价值更清晰）
4. 交接包生成（比 wiki 更容易产生价值）
5. 证据阅读 UI（来源页、证据跳转、冲突定位——是"判断界面"而非文档编辑器）

价值较低、可丢弃：完整 Web 产品壳、泛需求管理叙事、GitHub/Gitea 登录（除非服务于交付/执行闸门）。

---

## 八、验证路径（唯一的下一步，最低成本）

**本决策的全部结论仍是假设，不是已验证事实。** 不立即立项重写。

验证方法：**下次跑一个真实 OPC idea 时，在"需求层产出交接给执行层"那一步，手动尝试用 WhyWiki 现有能力生成需求包 / 交接包**，观察它是帮上忙还是碍事。一次真实交接即可判断此定位是否成立。

- 成功信号：生成的需求包真的被 opc-dev 直接使用，且减少了来回澄清。
- 失败信号：生成物碍事、需大量手改、或 opc-dev 宁可不用。

WhyWiki 的命运，绑定在 OPC 工作流第一次真实交接的那个瞬间。

---

## 九、元层收获（关于 OPC 工作流本身）

本次讨论是 OPC"需求层多声音讨论"的首次真实跑通，验证出一条关于工作流本身的结论：

> **多声音的价值不来自"多一个 Agent 在场"，而来自"有人被结构性地指派站对立面"。** 当 PO 与创始人高度同步（本次同步看空）时，需要的是一个被指派的反方（本次 Codex 当魔鬼代言人挖出了被双人共识掩盖的活路），而非更多附和。此模式应固化进 OPC 工作流：多声音用于对抗共识，不用于凑人数。
