# WhyWiki 项目主页与需求页 UI 设计

Date: 2026-05-25

## 背景

当前项目内默认页面把项目概览、产品说明、统计指标、推荐步骤、来源、事实、冲突和操作入口放在同一个 `需求现状` 视图里。这个结构对第一次打开项目的新用户认知负担过高，也让“需求现状”承担了过多页面职责。

本次设计目标不是增加一个装饰性的欢迎页，而是重新划分项目内信息架构：

- 项目主页负责安顿用户、说明项目当前状态、给出下一步。
- 需求页负责直接展示当前项目下的需求卡片。
- 来源、冲突、问答和设置作为用户任务入口保留，但不在默认页一次性摊开。

## 用户目标

用户打开项目后，应在 5 秒内知道：

1. 这是哪个项目。
2. 项目当前有没有接入来源。
3. 如果是空项目，下一步应该连接本地文件夹或 GitHub 仓库。
4. 如果项目已有内容，当前最需要关注的需求是什么。
5. 需求是否有来源、是否冲突、是否需要确认。

## 非目标

- 不把 WhyWiki 做成通用项目管理工具。
- 不把需求页做成复杂告警中心。
- 不在第一版自动判断“业务关键需求”。系统可以判断冲突、待确认、来源覆盖和用户最近操作，但不能可靠判断业务重要性。
- 不强行把内部 `facts` 数据模型立即重命名。第一阶段可以保持后端 API 与表结构稳定，同时在 UI 层建立“需求”语义。

## 信息架构

项目内一级导航调整为：

1. `主页`
2. `需求`
3. `冲突`
4. `来源`
5. `问答`
6. `设置`

设计意图：

- `主页` 是打开项目后的稳定锚点。
- `需求` 替代当前面向用户暴露的“事实”概念，展示当前项目下的需求卡片。
- `冲突` 放在 `来源` 前面，因为它更接近需要用户处理的事项。
- `来源` 替代 `证据` 作为一级入口。用户更容易理解“这条需求从哪里来”。
- `问答` 保留为基于来源和需求的提问入口。
- `设置` 保留低频操作，例如诊断、导出和本地配置。

## 项目主页

打开任何项目后，默认先进入项目主页。

项目主页不是大而全 dashboard，而是“项目锚点 + 需求预览”：

- 显示项目名称。
- 显示当前状态，例如未连接来源、已连接来源但未生成需求、已有需求待确认、存在冲突。
- 空项目时，主行动是连接来源，支持本地文件夹和 GitHub 仓库。
- 已有内容时，显示 1 到 3 个最需要关注的需求预览。
- 提供主按钮 `查看全部需求`。
- 在主行动下方显示紧凑统计，例如来源数、需求数、冲突数、Wiki 页面数，但不让统计成为页面主角。

项目主页承担项目级信息。截图中类似 `Demo Project`、项目说明、状态 badge 和统计指标应从 `需求现状` 移到主页。

## 需求页

需求页只展示需求相关内容，不再混入项目概览。

### 页面结构

需求页由两层组成：

1. `需要处理`
   - 展示少量冲突、待确认或低可信需求。
   - 最多露出 2 到 3 张，避免页面长期呈现一片红色。
   - 目的是提醒用户有事项需要处理，而不是制造压迫感。

2. `全部需求`
   - 以卡片网格展示当前项目下所有需求。
   - 默认使用稳定排序，例如来源顺序或生成顺序。
   - 用户可以通过筛选 chips 快速切换视角。

### 需求卡片

需求卡片第一层使用业务可读语言，而不是系统事实语言。

第一层展示：

- 需求标题或简短陈述。
- 简短说明。
- 状态标签：`冲突`、`待确认`、`已确认`、`有来源`、`低可信`。
- 来源数量或主要来源摘要。

第二层详情展示：

- 原始来源文件或仓库。
- 证据片段。
- 关联 API、代码、部署说明、实验记录等支撑事实。
- 冲突原因。
- 确认、忽略或标记处理状态的操作。

设计原则：

- 用户第一眼看到的是“当前项目有哪些需求”。
- API、部署、代码、实验等事实不丢失，但作为需求的支撑信息和来源信息出现。
- 不把所有 facts 直接改名为需求，否则 API endpoint、部署约束和实验结果会和业务需求混在一起。

## 筛选

`全部需求` 标题与筛选 chips 在同一行：

- 左侧：`全部需求`
- 右侧：筛选 chips

筛选 chips 直接可点击，不使用折叠页或更多菜单。

初始 chips：

- `全部`
- `冲突`
- `待确认`
- `已确认`
- `最近操作`
- `按来源`

交互规则：

- 点击 chip 后选中，再次点击取消。
- 多个 chips 可以同时选中。
- 状态类筛选使用“或”关系，例如同时选择 `冲突` 和 `待确认` 时显示冲突或待确认需求。
- 状态类筛选再与排序或范围条件组合，例如 `最近操作` 或 `按来源`。
- 选中 chip 使用浅色底、边框和对应文字颜色。

颜色建议：

- `冲突`：红色。
- `待确认`：橙色。
- `已确认`：绿色。
- `最近操作`：蓝色。
- `全部` 和 `按来源`：中性色或主品牌色。

## 冲突跳转

需求页提供快速定位冲突卡片的跳转控件。

位置：

- 放在 `全部需求` 工具栏最右侧。
- 与筛选 chips 同一行。
- 不占用卡片网格的一整列。
- 不在项目主页显示，保持主页安静。

形态：

- 小胶囊控件，例如 `冲突 1/7` + 上下箭头。
- 箭头使用 Lucide/Feather 系 `chevron-up` 和 `chevron-down` 矢量图标。
- 不使用自制 CSS 箭头或文本箭头。

交互：

- 点击下箭头时，按页面阅读顺序从上到下、从左到右寻找下一个冲突卡片。
- 点击上箭头时反向寻找上一个冲突卡片。
- 跳转后滚动到卡片可见区域。
- 被定位的冲突卡片短暂高亮。
- 没有冲突时控件置为禁用，并显示 `冲突 0`。

## 术语调整

用户界面中减少或移除 `事实` 这个词。

建议替换：

- `事实与证据` -> `需求`
- `事实` -> `需求`，仅限需求页和用户可见文案。
- `证据` 一级入口 -> `来源`
- `确认这个事实` -> `确认这个需求`
- `已创建事实` -> `已生成需求`

内部仍可保留 `facts` 表、`/facts` API 和事实抽取服务，避免第一阶段引入大范围迁移风险。实现时需要通过 UI 层映射，把 `fact_type=requirement` 作为需求卡片主体，其它事实类型作为支撑信息或来源详情。

## 数据与逻辑影响

第一阶段实现可以使用现有数据：

- `facts` 中 `fact_type=requirement` 的记录作为需求卡片主体。
- `conflicts` 和 `facts.validity_status` 用于标记冲突状态。
- `facts.status` 用于标记待确认、已确认等状态。
- `evidence_json` 和 evidence API 用于展示来源和证据片段。
- 非 requirement 类型 facts 可在卡片详情中作为关联支撑事实展示，或留在 Wiki / 来源视图中。

后续如果需要更成熟的需求模型，可以再引入独立 `requirements` 聚合层，但不作为本次 UI 优化的前置条件。

## 空状态与错误状态

空项目主页：

- 标题说明当前项目还没有连接来源。
- 主按钮：`连接本地文件夹`。
- 次按钮：`连接 GitHub 仓库`。
- 说明 WhyWiki 会从来源中提取需求、冲突和可追溯 Wiki。
- `连接 GitHub 仓库` 必须接真实来源接入逻辑；如果实现阶段后端能力未完成，入口应显示明确的未接入状态和下一步，而不能假装连接成功。

需求页无需求：

- 如果没有来源，引导回项目主页连接来源。
- 如果有来源但未生成，主按钮为 `生成需求记忆`。
- 不只显示“暂无数据”。

来源或生成失败：

- 显示发生了什么、为什么影响需求生成、用户下一步可以做什么。
- 技术细节放日志或可展开详情。

## 测试与验收

实现后需要验证：

- 打开项目默认进入项目主页。
- 空项目主页展示连接来源动作。
- 已有项目主页展示 1 到 3 个需求预览和 `查看全部需求`。
- 一级导航顺序为 `主页 / 需求 / 冲突 / 来源 / 问答 / 设置`。
- 需求页不再显示项目级 hero 和大段产品说明。
- 需求页以卡片展示需求。
- 筛选 chips 可多选，并按预期更新需求列表。
- 冲突跳转按钮能跳到下一个和上一个冲突卡片。
- 无冲突时跳转控件禁用并显示 `冲突 0`。
- 中文和英文 i18n 文案保持同步。
- `python -m compileall whywiki` 通过。
- `python -m pytest -q` 通过。

## 文档影响

如果实现改变用户可见行为，需要同步检查：

- `docs/FEATURE_STATUS.md`

- `README.zh-CN.md`

README 和 README.zh-CN 是同步文档对；若公共行为、设置流程或产品定位变化，需要同改。
