# WhyWiki 需求生命周期与当前真相维护设计

Date: 2026-05-25

## 背景

WhyWiki 的用户可能在项目已经进行到一半时才开始导入材料。第一次导入会把新旧需求文档、会议纪要、代码、部署说明和实验记录一起带进来，因此系统会发现大量冲突。

第一次集中处理冲突是可以接受的，但处理完成后，产品不能让用户每天重新面对全部历史冲突。WhyWiki 需要维护一套“当前项目真相”：哪些需求当前有效，哪些需求已被替代，哪些来源只作为历史证据，哪些新变化会影响当前需求。

这不是把 WhyWiki 做成文档编辑器，而是在原始证据之上维护结构化的项目记忆。

## 产品原则

1. 原始材料不自动改写、不自动删除。
2. 被淘汰的需求不消失，而是保留为历史证据。
3. 用户解决冲突是一条新的项目知识，必须持久记录。
4. 当前需求集是结构化数据，Markdown / Wiki / 交接包只是生成视图。
5. Ask、Wiki 和 handover 默认使用当前有效需求，但可以解释历史需求为何被替代。
6. UI 必须清楚区分来源证据、系统抽取、AI 推断、用户确认和冲突裁决。
7. 用户选择中文时，状态、动作、标签、空状态、错误提示和生成文档标题应尽量使用中文。

## 非目标

- 不自动修改用户导入的原文档。
- 不要求用户手写维护一份最终需求大文档。
- 不做完整需求管理系统、Roadmap、排期或任务管理。
- 不做复杂版本树或企业级审批流。
- 不把 WhyWiki 变成 Notion / Confluence / Feishu 替代品。

## 核心概念

### 当前需求集

当前需求集是 WhyWiki 认定的“当前应该按哪套需求开发”的结构化集合。

它由三类信息组成：

- 系统从来源中抽取出的候选需求。
- 用户确认、拒绝、合并或替代需求时产生的裁决。
- 后续扫描发现的新证据、新冲突和需求变化。

当前需求集不是一份手写 Markdown。Markdown 只是当前需求集的导出和阅读形态。

### 决策记录

当用户解决一个需求冲突时，系统应写入决策记录。

决策记录至少表达：

- 用户选择了哪条需求作为当前有效需求。
- 哪些需求被替代、拒绝或仅保留为历史参考。
- 用户选择的原因或系统建议原因。
- 决策依据的来源和证据。
- 决策时间和操作者。

示例：

```text
2026-05-25，用户确认“移动端首屏必须支持离线缓存”为当前有效需求。
旧需求“移动端不做离线缓存”已被替代。
原因：新版产品方案覆盖旧版需求。
证据：docs/需求_v1.md、docs/需求_v2.md
```

### 来源材料状态

来源材料不等于当前真相。一个旧文档可能仍然有价值，但不应该继续指导开发。

来源材料需要有面向用户的状态：

- 当前可信：整体仍可作为当前依据。
- 部分过期：包含一些已被替代或已拒绝的需求。
- 已过期：整体不应作为当前开发依据。
- 存在冲突：与当前需求集或其它来源存在未解决冲突。
- 历史参考：保留用于追溯原因，不参与当前判断。

这些状态属于 WhyWiki 的项目记忆层，不写回原文档。

## 需求生命周期

内部可以继续使用英文枚举，避免破坏 API 和测试；用户界面和生成文档必须通过 i18n 显示本地化文案。

| 内部状态 | 中文 UI | English UI | 含义 |
| --- | --- | --- | --- |
| `candidate` | 候选需求 | Candidate | 系统从来源中抽取，尚未确认。 |
| `needs_review` | 待确认 | Needs review | 可信度不足、证据不完整或需要用户判断。 |
| `current` | 当前有效 | Current | 当前项目应按此需求执行。 |
| `confirmed` | 已确认 | Confirmed | 用户确认过，但不一定表达替代关系。 |
| `superseded` | 已被替代 | Superseded | 已被另一条当前有效需求覆盖。 |
| `rejected` | 已拒绝 | Rejected | 用户确认这条需求不应进入当前需求集。 |
| `historical` | 历史参考 | Historical | 保留作背景，不参与当前开发判断。 |
| `conflicting` | 存在冲突 | Conflicting | 与其它需求、代码、部署或来源存在冲突。 |

产品文案规则：

- 中文界面不要直接显示 `current`、`superseded`、`needs_review` 等枚举。
- 英文界面不要混入中文状态词。
- 文件路径、代码符号、API endpoint、证据原文和用户原文档标题保持原样。
- 日志、API response、测试 fixture 可以保留英文枚举，但主 UI、生成 Wiki、handover 和 Ask answer 应使用当前语言。
- 同一张卡片内不要混用 `Current 当前有效` 这类双语标签，除非是开发者诊断视图。

## 冲突解决动作

冲突页不应只有 `resolve` 和 `ignore`。需求冲突需要表达用户裁决。

首版动作：

1. 接受左侧需求为当前有效。
2. 接受右侧需求为当前有效。
3. 合并为新需求。
4. 标记两者都已过期。
5. 暂不处理。
6. 仅忽略此冲突。

当用户接受其中一条需求时，系统应自动完成：

```text
胜出需求 -> 当前有效 / 已确认
落败需求 -> 已被替代
冲突 -> 已解决
决策记录 -> 新增
来源材料 -> 重新计算是否部分过期
当前需求快照 -> 下次生成时更新
```

当用户选择“合并为新需求”时：

```text
新需求 -> 当前有效 / 已确认
原始冲突需求 -> 已被替代
冲突 -> 已解决
决策记录 -> 记录合并原因和来源
```

当用户选择“标记两者都已过期”时：

```text
两条需求 -> 历史参考或已拒绝
冲突 -> 已解决
决策记录 -> 记录不再适用的原因
```

## 当前需求快照

WhyWiki 需要生成一份“当前需求快照”，但它是结构化当前需求集的生成视图，不是唯一真相源。

快照内容：

1. 当前有效需求。
2. 每条需求的证据来源。
3. 用户确认状态。
4. 最近新增或变化的需求。
5. 最近被替代的需求。
6. 未解决冲突。
7. 包含过期需求的来源材料。
8. 最近一次扫描时间。
9. 最近一次人工裁决时间。

快照出现位置：

- 需求页：日常查看当前需求。
- Wiki `requirements` 页面：可读文档。
- Handover：新人理解当前项目状态。
- Ask：回答“当前需求是什么”时默认使用快照语义。

## 日常维护模式

首次导入后，用户进入整理模式：

```text
导入大量材料 -> 发现冲突 -> 集中裁决 -> 建立当前需求集
```

整理完成后，用户进入维护模式：

```text
重新扫描 -> 只提示新变化对当前需求的影响 -> 用户处理增量冲突
```

维护模式首页应表达：

```text
当前需求集稳定
本次扫描发现 5 条变化
其中 1 条可能影响当前需求
2 个旧来源包含过期信息
暂无阻塞冲突
```

中文模式下，上述状态应使用中文。英文模式下才使用英文。

## UI 影响

### 需求页

需求页默认展示当前有效需求，而不是全部历史抽取结果。

推荐分区：

- 当前有效
- 待确认
- 最近变化
- 已被替代
- 历史参考

“已被替代”和“历史参考”默认折叠，避免用户误把旧需求当成当前任务。

### 冲突页

冲突卡片应展示：

- 冲突的两组或多组需求。
- 每组需求的来源证据。
- 系统建议。
- 用户可执行的裁决动作。
- 裁决后会发生什么。

中文模式下，按钮应显示：

- 接受为当前需求
- 合并为新需求
- 标记为已过期
- 暂不处理
- 忽略此冲突

英文模式下，按钮应显示：

- Accept as current
- Merge into new requirement
- Mark outdated
- Leave for later
- Ignore this conflict

### 来源页

来源页应显示来源材料对当前需求集的影响：

```text
需求_最终版_旧.md
状态：部分过期
影响：其中 3 条需求已被新版需求替代
建议：不要作为当前开发依据
```

英文模式下：

```text
requirements_final_old.md
Status: Partially outdated
Impact: 3 requirements were superseded by newer requirements
Suggestion: Do not use this file as current development guidance
```

### Ask

当用户问当前需求时，Ask 默认回答当前有效需求。

当历史材料中有不同说法时，Ask 应说明：

```text
旧文档中确实出现过另一个需求，但它已被用户裁决为“已被替代”。
当前应以新版需求为准。
```

不要把历史需求和当前有效需求混在同一层级呈现。

## 数据与实现边界

第一阶段可以在现有 `facts` 和 `conflicts` 基础上扩展：

- 继续把 `fact_type=requirement` 作为需求主体。
- 扩展需求有效性语义，支持当前有效、已被替代、历史参考等状态。
- 为冲突解决增加结构化裁决记录。
- 根据需求状态反推来源材料状态。
- 生成当前需求快照时只读取结构化状态，不从 Markdown 反向解析。

如果现有 `status` 与 `validity_status` 难以表达全部语义，可以新增窄表或事件表，但不要引入完整企业级审批模型。

## 文案与本地化规范

WhyWiki 的主 UI 必须遵守语言选择。

规则：

1. 所有状态标签、按钮、空状态、错误恢复建议、生成文档标题都必须走 i18n。
2. 中文界面优先使用中文，不在主 UI 暴露英文枚举。
3. 英文界面使用英文，不混入中文状态词。
4. 证据原文不翻译，避免破坏可追溯性。
5. 文件名、路径、代码符号、API endpoint 不翻译。
6. AI 或系统生成的解释应遵循当前 UI 语言。
7. 测试必须覆盖关键状态词在中英文词典中同时存在。

推荐中文词汇：

- 当前有效
- 候选需求
- 待确认
- 已确认
- 已被替代
- 已拒绝
- 历史参考
- 存在冲突
- 部分过期
- 已过期
- 当前需求快照
- 决策记录

推荐英文词汇：

- Current
- Candidate
- Needs review
- Confirmed
- Superseded
- Rejected
- Historical
- Conflicting
- Partially outdated
- Outdated
- Current requirements snapshot
- Decision record

## 验收标准

产品验收：

- 用户解决冲突后，胜出需求进入当前需求集。
- 被淘汰需求不会删除，而是显示为已被替代或历史参考。
- 原始来源不被自动修改。
- 来源页能说明某个文档是否包含过期需求。
- 当前需求快照能说明当前有效需求和历史替代关系。
- Ask 回答当前需求时不会把旧需求当作当前需求。
- 中文模式下主 UI 不出现裸英文状态枚举。
- 英文模式下主 UI 不出现中文状态标签。

工程验收：

- 新增或变更状态必须有 i18n key。
- 状态转换有测试覆盖。
- 当前需求快照有测试覆盖。
- 冲突裁决记录有测试覆盖。
- 相关 README、功能台账和 UI 规范同步更新。
- `python -m compileall whywiki` 通过。
- `python -m pytest -q` 通过。

## 文档影响

后续实现时需要同步检查：

- `docs/FEATURE_STATUS.md`
- `docs/ui_ux_guidelines.md`
- `README.md`
- `README.zh-CN.md`
- `docs/first_board_design.md`

其中 `README.md` 和 `README.zh-CN.md` 是同步文档对。若公开产品行为、设置流程或功能状态改变，必须一起更新，并保持章节结构对齐。

## 设计自检

- 没有要求修改原始文档，保留 WhyWiki 的证据链。
- 没有把当前需求快照设为唯一真相源，避免退化成手写文档。
- 冲突解决后的淘汰语义明确，不靠 `ignored` 掩盖旧需求。
- 中文 / 英文状态文案规则明确，内部枚举和用户文案边界清楚。
- 首版范围仍围绕 WhyWiki 核心闭环：导入材料、生成知识、审查冲突、维护当前需求、输出带证据结果。
